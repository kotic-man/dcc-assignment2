[A2] RPC semantics
The service achieves at-most-once execution of the mutation. After a timeout the client cannot tell whether the request was lost or only the reply was lost, so it retries. Every logical operation carries a client-generated idempotency key, which stays the same across all retry attempts. The server checks this key in a deduplication store under the same lock that mutates the counter; a repeated key returns the stored result with was_duplicate = true and the delta is not applied again. Therefore a retry is safe: the counter changes at most once per logical operation.

[A3] Concurrency
The server handles clients in parallel with grpc.server(futures.ThreadPoolExecutor(max_workers=8)). All shared state (the counter values and the deduplication store) is protected by a single threading.Lock. The duplicate-key check and the counter update happen inside the same critical section, so two concurrent requests cannot both pass the check. This is verified by test_concurrent_increments_exact: two concurrent clients x 1,000 increments yield exactly 2,000.

[B1] Lamport clocks
Each process (client, replica) keeps its own logical counter in clocks.py. Before every local event (SEND, APPLY) the counter is incremented; on receiving a message it is set to max(own, received) + 1 before processing. The current value is attached to every outgoing message in the lamport_time field. Every event is written to the log in the required format, and the counter update and the log write happen under one lock, so the order of lines in a log matches the order of L values.

[B2] Happened-before analysis (trace: logs/b2_trace.txt, diagram: b2_diagram.png)
(1) Causally ordered pairs. First, client-2 SEND Increment(y) (L=1) happened before client-1 RECV IncrementReply(x=1) (L=8). Chain: client-2 SEND (L=1) -> replica-A RECV (L=2) by message; replica-A RECV (L=2) -> APPLY y=1 (L=3) -> SEND (L=4) -> RECV (L=5) -> APPLY x=1 (L=6) -> SEND (L=7) by local order on the replica; replica-A SEND (L=7) -> client-1 RECV (L=8) by message. The clients never talk to each other, but the replica handled client-2's request before replying to client-1, so the order is causal. Second, replica-A APPLY x=2 (L=12) happened before client-3 RECV GetReply(value=2) (L=16). Chain: replica-A APPLY (L=12) -> SEND (L=13) -> RECV Get (L=14) -> SEND GetReply (L=15) by local order; replica-A SEND (L=15) -> client-3 RECV (L=16) by message. This is why client-3 reads x=2.
(2) Concurrent pair. client-1 SEND Increment(x) (L=1) and client-2 SEND Increment(y) (L=6) are concurrent. The client-1 SEND is the first event of client-1, so nothing precedes it and client-2 SEND (L=6) cannot happen before it. In the other direction, the only path from client-1 goes through replica-A RECV (L=5), but the last message client-2 received before its SEND (L=6) was the reply sent at replica-A L=4, before that RECV, so it carries no information about client-1's request. The values L=1 < L=6 only reflect how the counters happened to advance: Lamport clocks guarantee that a -> b implies L(a) < L(b), not the converse, so a smaller L does not mean the event happened earlier, and the values cannot show that two events are concurrent.
(3) Limitation. Lamport clocks cannot distinguish causal order from concurrency: L(a) < L(b) does not imply a -> b. Vector clocks fix this, since two events are concurrent exactly when neither vector is componentwise less than or equal to the other.

[C1] Partial application of a failed write
If the client reports a failed write because only one replica acknowledged it, that replica has nevertheless applied the increment, so a later read from it returns the new value although the client was told the operation failed (a partially applied write). A consensus protocol such as Raft or Paxos prevents this: a value becomes visible only after a majority has accepted it in an agreed order, and an entry that reached only a minority is never served as committed.

[C1] Read consistency risk
Get reads from a single replica, so it can return a stale value if that replica missed a write (for example because it was down or slow). Reads are therefore not guaranteed to reflect the latest committed write.

[C3] Failure-injection results
Scenario 1: replica crash mid-request. Fault: replica crash-C is started with --fault crash-after-recv and terminates its own process when the first Increment arrives (real process death, deterministic trigger). Invariant: the client commits with 2 of 3 acks, no exception reaches the caller, both surviving replicas hold x=1, and the crashed process has exited. Evidence: test_replica_crash_mid_request_still_commits; logs/failures/crash-C.log contains the RECV line and no APPLY or SEND.
Scenario 2: request duplication. Fault: the same idempotency key is sent twice through the quorum client and once more directly to each replica. Invariant: the value stays 5 (not 10) everywhere and the direct resend returns was_duplicate = true. Evidence: test_duplicate_request_moves_value_once; DEDUP lines in logs/failures/dup-A.log.
Scenario 3: induced timeout with retry. Fault: replica timeout-A is started with --fault slow-first --delay-ms 1500, the client deadline is 0.5 s. Invariant: the first attempt hits DEADLINE_EXCEEDED, the retry with the same key succeeds (new_value = 1), and the delayed original request is later recognised as a duplicate, so the counter moved exactly once. Evidence: test_induced_timeout_retry_moves_exactly_once; logs/failures/timeout-A.log shows RECV, RECV, APPLY, SEND, DEDUP, SEND.
